1 Identidad digital

Una identidad digital es el conjunto de atributos que representan a alguien o algo en un sistema. No es la persona: es un modelo de ella con la misma intención que una llave copiada de una puerta original.

  • Puede ser parcial (solo "cliente", solo "empleado") según contexto.
  • Puede ser anónima, seudónima o vinculada a un usuario real.
  • Se compone de atributos (edad, rol, correo) y de identificadores (email único, ID).

Interpretación En un sistema de solicitudes, la "identidad" que importa es la capacidad de responder: ¿quién pide?, ¿qué puede ver?, ¿qué dejó registrado? La identidad técnica (la base de datos de usuarios) responde eso.

2 Autenticación

Autenticación responde a ¿quién eres?. Autentican: presentar una credencial que vincula la identidad con una prueba (algo que sabes, algo que tienes, algo que eres).

Algo que sabes → password Algo que tienes → teléfono, llave de seguridad Algo que eres → huella, rostro

Ejemplo ficticio: valentina@demo.local se autentica con un password — y solo el hash de ese password vive en la base de datos, nunca la palabra en claro.

3 Autorización

Autorización responde a ¿qué puedes hacer aquí? y ocurre después de autenticar. Autenticar no autoriza.

En el taller 05A la diferencia es central: un requester autenticado solo hace POST /requests, un agent además cambia estados y prioridades. Esa política vive en el backend; ocultar un botón en el frontend NO es autorizar.

Dato Un recurso pertenece a su autor/actor registrado; el sistema responde 404 ante recursos ajenos para no filtrar su existencia.

4 Auditoría

Auditoría es registrar qué pasó, quién lo hizo y cuándo para poder revisarlo después. No previene, documenta.

En el taller, cada cambio de estado de una solicitud crea una fila en el historial con changed_by tomado del token — no del cuerpo de la petición. Eso es auditoría mínima y honesta.

Interpretación Una tabla de auditoría solo sirve si nadie puede fingir el actor: por eso changedBy que llega en el body es rechazado (400 SERVER_CONTROLLED_FIELD).

5 Passwords

Punto de partida de casi toda identidad. Una regla técnica: nunca guardar la contraseña en claro; guardar un hash derivado con una función lenta (scrypt, bcrypt, argon2) + sal.

En el taller 03 se aprecia que el frontend solo envía el password, el backend hace el hashing y el frontend jamás recibe ni expone el hash. Ejemplo ficticio: la fila de valentina@demo.local guarda scrypt$demo$…, nunca v4l3nt1n@21.

  • Largo mínimo > complejidad forzada (16+ caracteres razonables).
  • Mismas 401 para usuario inexistente y password incorrecto: no revelar cuál falló (anti-enumeración).

6 Sesiones

Una sesión es estado de "autenticado" que dura desde el login hasta el logout/expiración, mantenido en el servidor (o derivado de un token firmado). El servidor decide cuándo revocarla.

  • Con estado: el servidor guarda la sesión (cookies HttpOnly).
  • Sin estado: el servidor valida la firma (JWT), no guarda nada.

Interpretación Las sesiones sin estado escalan sin memoria compartida, pero "revocar" un token firmado requiere listas negras o expirar la clave: la comodidad tiene costo.

7 Cookies

Pequeños datos que el navegador guarda y envía con cada petición al dominio. Útiles para transportar el identificador de sesión.

  • HttpOnly: JavaScript no las lee (defensa contra XSS).
  • Secure: solo por HTTPS.
  • SameSite: controla el envío entre sitios (CSRF).

Interpretación La cookie "recuerda" una sesión por dominio. En una SPA el token va a veces en memoria; la cookie HttpOnly es la alternativa común cuando el frontend no necesita leerlo.

8 Bearer tokens

Un token que otorga acceso y se envía en Authorization: Bearer <token>. "Bearer" = "el que lo porta puede pasar", sin más preguntas.

Dato La negligencia del portador (robo del token) es el riesgo principal, así que el canal debe ser HTTPS siempre.

  • Ventaja: el servidor no guarda estado por petición.
  • Costo: el token tiene vida útil corta (en el taller: expiresIn ≈ 3600 s).

9 JWT

Formato compacto de token firmado: tres segmentos base64url separados por punto — cabecera header.payload.signature.

  • Dato JWT es un formato, no una solución completa de seguridad.
  • Dato Decodificar no verifica: cualquiera lee el payload. Verificar = comprobar la firma.
  • Dato Firmado no es cifrado: la firma prueba integridad/origen, no oculta el contenido.

En el taller el backend verifica firma, emisor, audiencia y expiración del JWT en cada request (/auth/me, rutas de requests) con el algoritmo esperado HS256.

Ejemplo ficticio de payload (no uses tokens reales) 
{"id":"usr_2024_valentina","role":"requester","iat":1719000000,"exp":1719003600,"iss":"backend-course-api","aud":"backend-course-client"}

Inspector ficticio

Mira las tres partes de un JWT falso: se decodifican (cualquiera podría), pero nada aquí verifica la firma. Verificar vive en el servidor.

10 API keys

Secretos de larga vida que identifican a una aplicación o servicio, no a un humano. Común entre servidores.

  • Dato Suelen identificar la app, no la identidad del usuario final; no reemplazan la autenticación de personas.
  • Deben rotarse y tratarse como credenciales (nunca en el cliente).
  • Permiten scope y límites de uso por consumidor.

Interpretación Si una app de navegador la guardara en el bundle, cualquiera la podría leer: por eso la API key pública se mueve a un backend/proxy.

11 OAuth 2

Marco de autorización delegada: una app le da a otra acceso limitado a recursos de un usuario, sin revelar el password del usuario.

Dato OAuth trata sobre autorización delegada (scopes), no identidad. Flujos típicos: authorization code, client credentials, device.

Ejemplo ficticio: la app "Clima App" pide solo el alcance read:location a tu cuenta, nunca tu password.

12 OpenID Connect

OpenID Connect (OIDC) construye identidad encima de OAuth 2: añade el token de identidad (ID token, un JWT) que el cliente puede verificar para saber quién eres.

  • OAuth 2 = permisos sobre recursos (delegación).
  • OIDC = además, "quién soy" (autenticación).

Recomendación Para "iniciar sesión con Google/GitHub", OIDC es el protocolo moderno habitual, no una autenticación propia reinventada.

13 MFA

Multi-factor authentication: exigir al menos dos factores distintos (sabes + tienes, tienes + eres) para subir la barra de robo de credenciales.

  • App autenticator (TOTP) o llave de seguridad (FIDO2) > SMS.
  • Los códigos de recuperación permiten volver si pierdes el factor.

Interpretación MFA no es infalible: si el factor de "algo que tienes" es un SMS interceptable, la ganancia de seguridad es limitada.

14 Passkeys

Credenciales basadas en criptografía de clave pública (WebAuthn): el dispositivo guarda la clave privada, el servidor solo la pública.

  • El secreto no sale del dispositivo (resistente al phishing).
  • Sin password que robar: autentican con biometría o PIN.
  • Se sincronizan entre dispositivos de un mismo ecosistema.

Recomendación Cuando el público usa dispositivos modernos, passkeys son una opción de futuro cercano frente a passwords frágiles.

15 Proveedores de identidad

Un proveedor de identidad (IdP) es el servicio que autentica y emite credenciales verificables (Google, GitHub, un IdP corporativo…).

  • La app (SP/Cliente) delega en el IdP vía OIDC/SAML.
  • El usuario presenta el resultado (token de identidad) a la app.
  • Ventajas: no gestionas passwords ni hashes; el IdP sostiene MFA.

En la 05A aún se usa autenticación propia con hash scrypt; un IdP externo es alternativa estudiada, no implementada.

16 Autenticación propia vs gestionada

Construir autenticación propia (como la del taller) enseña el dominio, pero implica mantener hashing, tokens, revocación, recuperación y pishing-proofing. No siempre conviene.

Dato Gestionar passwords y sesiones es un riesgo de seguridad que muchos productos no necesitan asumir: un IdP maduro ya resolvió esos problemas.

Decisión mía Para 05A mantengo autenticación propia (objetivo pedagógico y de evaluación); en un producto real elegiría un IdP gestionado salvo requisito explícito de no-dependencia externa.

17 Riesgos comunes

  • Passwords en claro o hash débil (scrypt/bcrypt/argon2 correctos).
  • Exponer password_hash, tokens o secretos en respuestas.
  • Aceptar createdBy/changedBy del body (falsificar el actor — 400 en el taller).
  • Guardar solo el token en localStorage sin evaluar XSS.
  • Respuestas que distinguen email válido vs no (enumeración).
  • Recursos de otros expuestos con 403 en lugar de 404.
  • Ocultar botones y considerar eso "autorización" (no protege al backend).

18 Casos de uso

App interna de solicitudes

Autenticación propia + roles requester/agent + historial de auditoría. Es exactamente la 05A.

E-commerce para consumidores

IdP gestionado u OIDC social + MFA de alto riesgo (pagos).

API entre servidores

Client credentials / API keys por consumidor, no identidad de persona.

Cajero / alta sensibilidad

MFA + passkeys; la latencia y el factor humano dictan el flujo.
